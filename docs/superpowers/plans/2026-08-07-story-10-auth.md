## This story is bigger than the others. That is a decision, not an accident.

Story 10 was scoped as "auth screens". Two calls made during Story 9 review
widened it:

1. **Token storage moves off `localStorage`.** `plan.md` §14 marked this a known
   ceiling: the token is readable by any successful XSS. Fixing it is not a

   with it.
2. **Dark mode gets wired.** The `.dark` block has existed since Story 8 with no
   provider, and three controls measure below AA when it is forced on.

The screens themselves are the smallest part. **Split the PR after Task 4** if
the diff gets unwieldy: Tasks 1–4 are the auth contract, 5–7 are the UI.

## What is already decided — do not relitigate

- **Owner-scoped everything.** Every row is scoped off the verified token,
  never off a body or query parameter. Another user's id is a `404` byte-identical
  to a genuinely missing one.
- **Refresh tokens are join-row-shaped**, so their FK to `users` is `CASCADE`,
  not the `RESTRICT` that `tasks.ownerId` and `categories.ownerId` use. A
  refresh token has no value independent of its user. See `plan.md` §5 for why
  those two cases differ.
- **shadcn token vocabulary**, `type-*` for the type scale, and no colour that
  is not already in `index.css`.
- **Red primary, no gradients** (Story 9). Dark variants already exist for every
  token; they have simply never been rendered.

## The auth design

```
POST /auth/signup   201  { user, accessToken }  + Set-Cookie: refresh
POST /auth/login    200  { user, accessToken }  + Set-Cookie: refresh
POST /auth/refresh  200  { accessToken }        + Set-Cookie: refresh (rotated)
POST /auth/logout   204                         + Set-Cookie: refresh (cleared)
GET  /auth/me       200  user                   Bearer, unchanged
```

**Access token** — JWT HS256, `sub` = user id, 15 minute expiry, returned in the
body and held only in a module variable in the browser. Never persisted. An XSS
that runs can still read it, but it dies in 15 minutes and cannot be refreshed
without the cookie it cannot read. That is the whole point of the design; do not
"helpfully" cache it in `localStorage`.

**Refresh token** — opaque, 32 random bytes from `node:crypto`, base64url. Not a
JWT: it carries no claims, it is a lookup key, and making it a JWT would only
add a signature to something that must be checked against the database anyway.

**Only its SHA-256 hash is stored.** A leaked database dump then yields no usable
tokens. Plain SHA-256 rather than scrypt is correct here and wrong for passwords:
this is 256 bits of uniform randomness, so there is no dictionary to run.

**Rotation on every refresh, with reuse detection.** Each refresh revokes the
presented token and issues a successor in the same `familyId`. Presenting an
already-revoked token means either a replay or a stolen cookie, and the honest
response is to revoke *the entire family* — logging out the real user too. That
is the intended behaviour, not collateral damage: it is the only signal
available that a token was stolen.

### Cookie attributes, and why each one

| Attribute | Value | Why |
|---|---|---|
| `HttpOnly` | always | The entire point. Script cannot read it. |
| `Secure` | production only | A `Secure` cookie is dropped over plain http, so setting it unconditionally breaks local development silently. |
| `SameSite` | `Strict` | The app is same-origin in both dev (Vite proxy) and production (`SpaAdapter`), so nothing legitimate needs a cross-site send. |
| `Path` | `/api/v1/auth` | The cookie is not attached to every task request — it is only needed by refresh and logout. |
| `Max-Age` | refresh TTL | Matches `expiresAt` in the row, so the browser and the database agree. |

**CSRF.** `SameSite=Strict` is the primary defence. Defence in depth: `/refresh`
and `/logout` reject a request whose `Origin` header is present and does not
match the host. Absent `Origin` is allowed — some non-browser clients omit it,
and `SameSite` already covers the browser case.

### Task 1: The `refresh_tokens` table

**Files:** create `server/src/db/schema/refresh-tokens.ts`; modify
`server/src/db/schema/index.ts`, `relations.ts`; generate a migration.

- [ ] **Step 1: Schema.**

```
refresh_tokens
  id            text uuid PK
  userId        text → users.id, not null, ON DELETE CASCADE, ON UPDATE CASCADE
  familyId      text not null            -- rotation lineage
  tokenHash     text not null, UNIQUE    -- sha256(token), never the token
  expiresAt     integer timestamp_ms, not null
  revokedAt     integer timestamp_ms, nullable
  replacedById  text nullable            -- successor, for auditing a chain
  createdAt / updatedAt
  INDEX (userId), INDEX (familyId)
```

- [ ] **Step 2: `pnpm --filter ./server db:generate`,** and read the emitted SQL
  before committing it. Confirm the FK really says `on delete cascade` — the
  clause is inert without `PRAGMA foreign_keys = ON`, which this codebase sets
  at connection time.

- [ ] **Step 3: Test the cascade at the HTTP level,** the way
  `modules/tasks/__tests__/cascade.test.ts` already does for the other three FKs.

### Task 2: Server — issue, rotate, revoke

**Files:** create `server/src/modules/auth/refresh-tokens.repository.ts`,
`server/src/modules/auth/cookies.ts`; modify `tokens.ts`, `auth.service.ts`,
`auth.controller.ts`, `server/src/config/*` (env).

- [ ] **Step 1: Env.** `JWT_EXPIRES_IN` becomes `ACCESS_TOKEN_TTL` (default
  `15m`) and `REFRESH_TOKEN_TTL` (default `30d`). Update `.env.example`. A
  7-day *access* token is exactly what this story exists to remove, so leaving
  the old name pointing at the new meaning would be a trap.

- [ ] **Step 2: `Tokens`** signs short-lived access tokens (unchanged otherwise —
  keep the `algorithms` pin and `requiredClaims: ['exp']`, both of which have
  tests) and gains `mintRefresh()` returning `{ token, hash, expiresAt }`.

- [ ] **Step 3: `RefreshTokensRepository`** — `create`, `findByHash`,
  `revoke(id, replacedById)`, `revokeFamily(familyId)`, `deleteExpired()`.

- [ ] **Step 4: `AuthService.refresh(token)`** in a **single transaction**
  (`db.transaction()` is synchronous here — see `server/.agents`):
  1. hash → `findByHash`. Miss → 401.
  2. `revokedAt` set → **reuse**: `revokeFamily`, 401.
  3. expired → 401.
  4. otherwise revoke this one, insert its successor, return both tokens.

- [ ] **Step 5: Cookie helpers** in `cookies.ts`, with the attribute table above
  encoded once. `Secure` is driven by `getEnv('NODE_ENV') === 'production'`.

- [ ] **Step 6: Controller.** `/refresh` and `/logout`, both `@ApiPublic()`
  (they authenticate by cookie, not by bearer), both behind the Origin check,
  and `/refresh` behind the existing rate limiter.

- [ ] **Step 7: Verify by mutation.** Each of these must fail when its control is
  removed, and the removal must be tried:
  - reuse of a rotated token revokes the family
  - an expired refresh token is rejected
  - logout revokes, so the cookie cannot be replayed afterwards
  - the cookie is `HttpOnly`, and `Secure` under `NODE_ENV=production`
  - a mismatched `Origin` is rejected
  - the refresh token never appears in a response body
  - the access token's `exp` is minutes away, not days

### Task 3: Client — in-memory token and single-flight refresh

**Files:** rewrite `web/src/lib/token.ts`; modify `web/src/lib/api.ts`; create
`web/src/features/auth/session.ts`.

- [ ] **Step 1: `token.ts` holds a module variable.** Delete every
  `localStorage` call. The `ponytail:` comment describing the old ceiling goes
  with it — it documented a decision that no longer exists.

- [ ] **Step 2: Boot.** Memory is empty after a reload, so the app calls
  `/auth/refresh` once at startup. **Until that resolves, do not render the
  router** — otherwise `ProtectedRoute` sees a null token and bounces a signed-in
  user to `/login` on every hard refresh of `/app`.

- [ ] **Step 3: 401 handling, single-flight.** On a 401 that is not itself from
  `/auth/refresh`: await one shared refresh promise, then retry the original
  request exactly once. Concurrent 401s must produce **one** refresh, not one
  each — a board view firing five queries at once is the normal case, and five
  parallel rotations would revoke each other and log the user out.

- [ ] **Step 4: Test the single-flight property specifically.** Fire several
  concurrent 401s against a mocked endpoint and assert the refresh endpoint was
  called once. Then break it (drop the shared promise) and confirm the test
  fails — this is the exact bug that looks fine in every manual test.

## Verification summary

| Check | Passes when | Mutation that must break it |
|---|---|---|
| Reuse detection | A replayed refresh token revokes its family | Remove the `revokedAt` branch → replay succeeds |
| Cookie flags | `HttpOnly` always, `Secure` in production | Drop the flag → test reports it |
| Origin check | Mismatched `Origin` is rejected | Remove the check → cross-origin refresh succeeds |
| Single-flight | N concurrent 401s cause 1 refresh | Drop the shared promise → N refreshes |
| Boot refresh | Hard refresh of `/app` stays signed in | Render the router before refresh resolves → bounces to `/login` |
| Dark contrast | 0 failures in both themes | Regress a token → failures reported |
