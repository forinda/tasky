# Story 11 — Board Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The board at `/app` — three status columns, task cards, filter chips, and a detail sheet that creates, edits, and deletes. The first screen where the API built in Stories 2–6 is actually used.

**Depends on:** Story 10 (merged).

---

## Two decisions taken before starting

**1. `categoryId` joins the server's filter allow-list.** `plan.md` §14 wants
filter chips that each map to one `ctx.qs` filter, but the allow-list is
`status` and `priority` only — category lives on a separate route,
`/categories/:id/tasks`. Building the chip row on two different mechanisms would
make one chip behave unlike the others: not combinable with the rest, a
different request path, one category at a time. The chips are supposed to be the
honest, visible answer to "why am I seeing three tasks", so they need one
mechanism.

**2. Categories management is not in this story.** The list, inline create,
colour picker, rename, and delete-with-confirm are their own screen. Story 10
was scoped as "auth screens" and became six commits across two packages; this
one stays reviewable. The board reads categories, it does not manage them.

## A bug to fix while adding the filter

`TasksService.assertKnownFilterValues` currently reads:

```ts
const allowed = FILTER_ENUMS[filter.field]
if (!allowed) continue          // ← skips the operator check too
if (filter.operator !== 'eq') throw …
```

`categoryId` has no enum, so it would hit that `continue` and **never reach the
operator check**. `?filter=categoryId:neq:<id>` would then be silently treated
as `eq` and return the exact inverse of what was asked — a wrong answer the
client cannot detect. That is the same bug the comment right above it was
written about, and adding a non-enum field is what re-opens it.

The operator check must run for **every** filterable field; the enum check only
where an enum exists.

## What is already decided — do not relitigate

- **Owner scoping is the base of every query**, never appended after. See
  `TasksRepository.scope`.
- **Unknown and unowned are reported identically** — a distinct message lets a
  client probe for other users' ids one 422 at a time.
- **Card anatomy** (§14): title at full weight on its own line, then one dense
  row of small meta. Not the Slack Lists treatment of labelling every field.
- **Empty columns stay visible** with a persistent add affordance. A column that
  vanishes when emptied hides the fact that it exists. `EmptyState` already
  exists for this and is the component the design brief calls the signature.
- **Drag-and-drop is Story 12.** Status changes here go through the detail sheet.
  The board must be fully usable without drag — that separation is the whole
  reason 12 is its own story.

### Task 1: Server — `categoryId` filter

**Files:** modify `server/src/modules/tasks/tasks.constants.ts`,
`tasks.repository.ts`, `tasks.service.ts`; add tests.

- [ ] **Step 1: Fix the operator check** so it runs for every filterable field,
  per the section above. Add a test for `?filter=categoryId:neq:<id>` returning
  422 **before** implementing the filter, so the fix is what makes it pass.

- [ ] **Step 2: Allow-list.** `filterable: ['status', 'priority', 'categoryId']`.

- [ ] **Step 3: Predicate.** An `EXISTS` sub-select against `task_categories`,
  not a join — a join against a many-to-many multiplies rows and would break the
  count in the pagination envelope:

```ts
case 'categoryId':
  return exists(
    db.select({ one: sql`1` })
      .from(taskCategories)
      .where(and(
        eq(taskCategories.taskId, tasks.id),
        eq(taskCategories.categoryId, filter.value),
      )),
  )
```

- [ ] **Step 4: No existence validation, deliberately.** A category id that is
  not yours simply matches nothing, because the query is already owner-scoped
  and the link belongs to the task. Rejecting unknown ids with a distinct error
  would hand back the enumeration oracle §14 closes everywhere else. Write the
  test that proves a foreign category id returns an empty list rather than an
  error or another user's tasks.

- [ ] **Step 5: Verify by mutation.** Remove the owner predicate → the
  cross-owner test must fail. Swap `EXISTS` for a join → the pagination `total`
  must go wrong for a task in two categories.

### Task 2: Client data layer

**Files:** create `web/src/features/tasks/{keys,queries,mutations}.ts`,
`web/src/features/categories/{keys,queries}.ts`.

- [ ] **Step 1: Keys mirror endpoint paths**, per the existing `authKeys`
  comment, and include the filter state — two different filter sets are two
  different cache entries, not one entry that flickers.

- [ ] **Step 2: One query per column.** Three status-filtered requests rather
  than one list partitioned in the browser. The server paginates; a client-side
  split would silently show "the first 20 tasks, distributed" and look correct
  while hiding the rest.

- [ ] **Step 3: Mutations** for create, update, delete, invalidating the affected
  column keys. Do not hand-roll optimistic updates yet — get it correct first;
  Story 12 needs them for drag and can add them where they earn their place.

### Task 3: Board UI

**Files:** create `web/src/routes/board.tsx`,
`web/src/components/board/{column,task-card}.tsx`; replace the `Board`
placeholder.

- [ ] **Step 1: Three columns**, header of coloured status dot + name + count.
  The dot never carries meaning alone — the name is always beside it.

- [ ] **Step 2: Task card** per §14, reusing `Pill`.

- [ ] **Step 3: Empty columns** get `EmptyState` with an instruction, not a
  label, and the add affordance inline.

- [ ] **Step 4: Loading and error states.** A board that renders three empty
  columns while loading is indistinguishable from a first-run board — the exact
  "working app reads as broken" failure §14 names. Use `Skeleton`.

- [ ] **Step 5: Mobile.** Columns scroll horizontally inside their own
  container; the page itself never scrolls sideways.

### Task 4: Filter chips

**Files:** create `web/src/components/board/filter-bar.tsx`.

- [ ] **Step 1: Filter state lives in the URL** (`useSearchParams`), not in
  component state. A filtered board should survive a refresh and be shareable;
  state that evaporates on reload is a worse answer than no filter at all.

- [ ] **Step 2: A chip per active filter**, dismissible, plus "Clear all" when
  more than one is active.

- [ ] **Step 3: Category chips use the `Combobox`** built in Story 8 — this is
  the searchable-select case it was ported for.

- [ ] **Step 4: Filtered-empty is not the same as empty.** A column with no
  results under a filter must say so and offer to clear it, not show the
  first-run "Add your first task". Getting this wrong tells someone their data
  is gone.

### Task 5: Task detail sheet

**Files:** create `web/src/components/board/task-sheet.tsx`.

- [ ] **Step 1: A `Sheet`, not a route.** §14 is explicit. Focus trapping and
  Escape were verified in Story 8; do not rebuild them.

- [ ] **Step 2: Title, description, priority, status, categories** (multi-select
  via `Combobox`), and delete behind a confirm that says what survives.

- [ ] **Step 3: Status change from here** is how a task moves between columns
  until Story 12.

- [ ] **Step 4: Create reuses the same sheet** where it sensibly can. Two
  near-identical forms drift apart within a story or two.

### Task 6: Proof and PR

- [ ] Contrast, focus ring, keyboard, and 320px on the board, **in both themes**.
- [ ] Filter round-trip: apply, reload, the same board comes back.
- [ ] Create, edit, move between columns, delete — each reflected without a
  manual refresh.
- [ ] A task in two categories appears correctly under a category filter, and
  the pagination total is right.
- [ ] `pnpm run test`, `pnpm typecheck`, `pnpm build`.
- [ ] Commit, push, PR.

## Verification summary

| Check | Passes when | Mutation that must break it |
|---|---|---|
| Owner scoping | Bob's board never shows Alice's tasks | Remove the owner predicate → cross-owner test fails |
| `categoryId` operator | `neq` is a 422 | Restore the early `continue` → it silently returns the inverse |
| Foreign category id | Empty list, not an error | Add existence validation → enumeration oracle returns |
| EXISTS not join | `total` correct for a task in 2 categories | Swap to a join → the count doubles |
| Filter in URL | Reload restores the board | Move it to component state → reload clears it |
| Filtered-empty | Says "no matches", offers to clear | Reuse the first-run empty state → reads as data loss |
